RELEASE GUIDE · OVERVIEW

Stockroom Release Guide

Increment 2 · Version 0.2.0 · 12 November 2026

Stockroom is a fictional electronics and workspace store built for your QA portfolio. This release lets customers browse, use a cart, place orders, and view their own purchase history. Operations staff can inspect inventory. It includes real login sessions and APIs, so you can practise UI, API, and hybrid testing.

This guide records what is available, the rules it follows, and what you can test. Future increments will add dated release entries and their own expected behaviour. It contains no test code.

Open the application

  1. Open the Stockroom application repository folder.
  2. Double-click Start Stockroom.cmd. Keep its terminal window open while using the application.
  3. Open http://127.0.0.1:3000 in your browser.
  4. Find your generated accounts and passwords in .local/demo-accounts.txt. This local file is excluded from Git.
  5. Sign in with a customer or staff account. To stop the application, press Ctrl+C in its terminal.

Use 127.0.0.1 consistently. Using localhost instead gives the browser a different application address and can cause sign-in protection to reject a request.

Scope of this release

All products, names, and accounts are fictional. The store uses English and EUR. Customers can now use a cart and place orders. Payments, registration, password recovery, shipping, cancellations, and staff order processing are not available in this increment.

The learner maintains and publishes the separate Playwright TypeScript automation framework. Application delivery does not add or modify those tests. New regression tests are written manually by the learner with explanations in the QA chat.

RELEASE GUIDE · ACCOUNTS

Accounts and access

There are two customer accounts and one operations staff account. Their passwords are generated separately for this installation. Signing in as one role must never grant the permissions of another.

Account Allowed behaviour
customer@stockroom.test
second@stockroom.test		 Browse and filter the catalog, read product details, use the cart, place orders, view your own orders, and sign out.
staff@stockroom.test Use the catalog and product details, plus the read-only inventory page containing supplier and unit cost information.
Signed-out visitor View the sign-in page and API reference. Protected pages lead to sign-in; protected APIs reject access.

Sign-in rules

  • Email and password are required. The browser checks an email's format before submitting the form.
  • Email is case-insensitive, and spaces around it are ignored. Passwords are case-sensitive and are not trimmed.
  • The Show or Hide control changes password visibility. It does not change the submitted password.
  • Successful sign-in opens the catalog. An already signed-in visitor opening the sign-in page returns to the catalog.
  • A wrong password and an unknown email produce the same incorrect-credentials message.
  • After five unsuccessful attempts for the same email within 15 minutes, further attempts are temporarily rejected. A successful login before that threshold clears that email's failure count.
  • The local installation also permits at most 30 login attempts per minute across all accounts. This protects the local service and may affect repeated testing.

Session and sign-out rules

A session expires after 30 minutes without a request to a protected page or API, or after eight hours in total. The next protected request after expiry is rejected. Simply keeping a page open does not refresh a session. Closing the browser is not a substitute for signing out.

Sign out ends the current browser session on the server and returns to sign-in. Reusing its old session must fail. Other independently signed-in sessions are unaffected.

Permission boundaries

A customer sees no Inventory navigation link. Opening the inventory page directly shows an access-denied message. Calling the inventory API directly as a customer returns status 403 and no inventory data. Customer catalog responses omit supplier and unit cost fields, including when a staff member browses the catalog.

Things to explore: valid and invalid login, empty fields, password visibility, email spacing and case, signing out, direct navigation, and different roles in separate browser sessions.

RELEASE GUIDE · CATALOG

Catalog and product rules

The starting dataset contains 24 products and 323 available units across Accessories, Audio, Computers, Displays, and Workspace. Six products have low stock and three are out of stock. Product counts refer to distinct products, not the number of available units.

Control Expected behaviour
Search Enter part of a product name or its SKU and submit Search or press Enter. Matching ignores letter case and spaces around the search. Maximum length is 100 characters. Symbols such as % and _ are treated as normal text.
Clear search Choose × (Clear search), or delete all search text, to remove the applied search immediately without submitting again. Keep category, availability, sorting, and page size; return to page 1. Results, count, summary, and address update together. With default filters, this restores the first six of all 24 products. An earlier search finishing late must not replace the cleared results. Use Tab to reach Clear search and Enter or Space to activate it; focus returns to the search input.
Category Choose one category or All categories. The selected category combines with the submitted search and availability filter.
Availability In stock includes any quantity above zero. Low stock means 1 to 5 inclusive. Out of stock means zero. All availability includes everything.
Sorting Sort by name, price, or stock, in either direction. Equal values use product ID in ascending order, giving predictable results across pages.
Pagination Six products per page by default. Choose 6, 12, or 24. Previous is unavailable on the first page; Next is unavailable on the last.
Changing criteria Submitting search or changing a filter, sort, or page size returns to page 1. Typing nonempty search text still requires Search or Enter; clearing is immediate.
Reset filters Clear search and filters, restore name A to Z, page 1, and six products per page.
No matches Show a clear empty result message and a way to clear filters. Do not show unrelated products.

Active criteria are reflected in the address bar. Reloading that address preserves them. The result count and range describe the filtered collection. A manually entered page beyond the last page has no items and offers a return to the first page.

Useful starting examples

Searching SR-101 finds Arc mechanical keyboard, priced at EUR 129.00 with 18 units. Combining Accessories with Low stock finds Dock USB C hub, priced at EUR 79.00 with 5 units. Clarity webcam is out of stock. These records let you compare catalog cards, product details, and API responses.

Product details and staff inventory

Opening a product shows its name, SKU, category, price, description, availability, quantity, and specifications. A missing product shows a not-found page. Prices use two decimal places in the UI; APIs use whole cents, so 12900 means EUR 129.00.

Staff inventory supports the same search submission, immediate clearing, filtering, sorting, and pagination. Its summary always describes the whole inventory, even when the table is filtered. This release displays stock and supplier information without providing editing controls.

RELEASE GUIDE · BASELINE API

API access and testing opportunities

Open http://127.0.0.1:3000/docs for Swagger. Expand an operation, choose Try it out, enter the required values, and execute it. Requests use the same account cookies as the application in that browser. Swagger automatically obtains the protection token needed for login and logout.

Operation Purpose Main expected outcomes
GET /api/auth/csrf Prepare protection for a sign-in or sign-out request. 200 and a protection token.
POST /api/auth/login Sign in with email and password. 200 success; 401 wrong credentials; 422 invalid fields; 429 too many attempts.
GET /api/auth/session Read the current account. 200 signed in; 401 signed out or expired.
POST /api/auth/logout End the current session. 204 success with no response body.
GET /api/products Search, filter, sort, and page through products. 200 results; 401 signed out; 422 invalid query values.
GET /api/products/{id} Read one product. 200 product; 404 missing product.
GET /api/categories Read categories and their full-catalog counts. 200 category list.
GET /api/inventory Read staff stock, cost, and supplier data. 200 staff; 403 customer; 401 signed out.
GET /api/health Check whether the application responds. 200 and status ok.

Login and logout also reject requests with missing or invalid protection tokens or the wrong Origin. Direct API clients must keep the cookies, obtain a token, and send both that token and Origin matching the application address. The protection token changes after successful login. Swagger explains the exact fields.

What to inspect in the Network tab

Open browser developer tools and select Network. Sign in, submit searches, or change filters. Inspect the endpoint, method, status, query values, request payload, and response. Product details are rendered by the server, so opening that page does not require a separate browser product API request. You can still call the product API independently.

Suggested testing approaches

  • UI: check login, catalog controls, product navigation, empty results, keyboard access, and staff navigation.
  • API: check invalid input, stock boundaries, totals, ordering, missing products, permissions, and session behaviour.
  • Hybrid: authenticate through the API and use the same session in the browser; compare a filtered API list with visible products; compare a product API response with its details page.

Increment 2 adds the cart and order APIs described below. Stock changes happen through accepted orders; there is no web stock editor. Requests sent directly by Playwright's API client run outside the browser page and will need their own request and response evidence in your future framework.

INCREMENT 2 · CART AND ORDERS · 12 NOVEMBER 2026

Shopping pages and behaviour

Page What the customer can do
Catalog Choose Add to cart on an available product to add one unit. Adding the same product increases its existing quantity. Out-of-stock buttons are unavailable. Search, filtering, sorting, pagination, and immediate search clearing continue to work.
Product details Choose a whole-number quantity from 1 to 99, then Add to cart. The resulting cart quantity must not exceed current stock or 99 units for that product.
Cart · /cart See current unit prices, quantities, line subtotals, available stock, and the total. Edit a quantity and choose Update, or Remove a product. Quantity zero does not remove an item: use Remove. Refresh cart retrieves the latest prices and stock. The cart is saved on the server for this account, including after logout and sign-in.
Confirmation Place order saves one order, updates stock, empties the cart, and opens a confirmation with the order number and saved details. No payment is collected.
My orders · /orders See only your own orders, newest first. The default page size is six. Open an order number for its details. No orders and an out-of-range page have useful empty states.
Order details · /orders/{id} See the saved product names, SKUs, quantities, unit prices, subtotals, total, date, and Placed status. Changes to the catalog do not rewrite an old order.

Business rules

  • Account ownership: shopping is for signed-in customers. Staff can inspect inventory but cannot use customer carts or orders. A cart belongs to the signed-in account; the API does not accept an owner ID. Another customer's order and a nonexistent order both return 404.
  • Totals: the server calculates each line as quantity × current unit price and adds those lines. Amounts are integer EUR cents in the API, formatted as EUR in the UI. No shipping fee, discount, or additional tax is added in this demo. A client cannot supply its own prices, totals, or order status.
  • Limits: 1–99 whole units per product, no more than available stock when adding or updating, and up to 50 different products. Blank, fractional, negative, string, and excessive quantities are rejected. Remove uses its own operation.
  • No reservation: adding, updating, and removing cart lines do not change stock. Two customers may have the same units in their carts. Availability is checked again at placement; there is no promise of stock before then.
  • Price changes: cart reads use current catalog prices and mark a price that differs from when the line was first added. The customer reviews the current total. If any price changes after that review, Place order returns 409 PRICE_CHANGED and creates no order. Refresh and review the new amount before trying again, even for a price decrease.
  • Stock changes: a reduction that still covers the requested quantity permits placement. Insufficient stock returns 409 STOCK_CHANGED, creates no order, changes no stock, and leaves the cart available for correction. The customer must reduce the quantity or remove the item. Increasing stock never increases a cart quantity automatically.
  • Atomic placement: all order lines, total, stock deductions, cart clearing, and duplicate protection succeed together or none do. Stock cannot go below zero. Refresh or reopen inventory to see changes after accepted orders; the original seeded total of 323 units is only the reset starting value.
  • Status: Placed means the order was accepted and stock was deducted once. It does not mean paid, shipped, or delivered. There are no cancellation, refund, or status-change operations in increment 2.
  • Duplicate protection: the browser disables repeated submission. The server also protects retries and two tabs ordering the same reviewed cart. A first successful request returns 201; an exact replay returns 200 with the same order and no second stock deduction. After another tab changes the cart, a stale review returns 409 CART_CHANGED.
  • Lost confirmation: if the response is lost, Retry order confirmation resends the original attempt rather than creating another. This attempt survives a reload in the same browser tab when session storage is available. My orders also lets the customer check whether an order exists.

INCREMENT 2 · API AND MANUAL QA

Real cart and order APIs

All operations below require a customer session. Mutations also require the exact Origin and a fresh X-CSRF-Token with its matching cookie. Swagger fills and refreshes the CSRF header for POST, PATCH, and DELETE. Request bodies are limited to 16 KiB. All responses use no-store and include X-Request-ID.

Operation Purpose and example
GET /api/cart Read your cart. Keep the returned version and checkoutToken for the reviewed prices.
POST /api/cart/items Add units: {"productId":"arc-keyboard","quantity":2}. Returns the current cart, with a subtotal of 25800 cents for two keyboards at the starting price.
PATCH /api/cart/items/arc-keyboard Replace the quantity: {"quantity":3}. Requires a line in your own cart.
DELETE /api/cart/items/arc-keyboard Remove your line. Send no request body. A repeated removal returns 404.
POST /api/orders Send {"cartVersion":the reviewed version,"checkoutToken":"the actual returned token"} and an Idempotency-Key header containing a new UUID. Use the same key and body for retries. Example Swagger tokens and order IDs are illustrative, not usable saved records.
GET /api/orders Read only your orders. Optional page and pageSize (6, 12, or 24). Unknown or repeated query parameters are rejected.
GET /api/orders/{id} Read your own saved order. Another customer's order returns the same 404 as a nonexistent order.

Typical errors are 401 without a session; 403 for staff, invalid CSRF, or a wrong Origin; 404 for a missing line, product, or owned order; 422 for invalid input; and 409 for insufficient stock, an empty or changed cart, a changed price, or a reused request key with different details. Failed placement leaves all stock unchanged. Swagger includes concrete success and error examples.

Useful independent checks

  • Add from both catalog and details; add the same product twice; update and remove; compare every UI subtotal and total with the API. Try zero, 100, a decimal, a string quantity, an unknown product, a forged total, and an out-of-stock product.
  • Use the two customer accounts to check separate carts and histories. Try another customer's order URL and API ID, a staff session, no session, a missing token, and a wrong Origin on each mutation.
  • Place an order; verify its confirmation, empty cart, My orders entry, saved details, and the exact stock reduction in catalog and staff inventory. Reloading confirmation must not place another order.
  • Repeat the same placement request; reuse its key with a different body; place the same reviewed cart concurrently from two tabs; and have two customers compete for the last unit. Check both the order count and the final stock.
  • Change a price or stock after adding or reviewing the cart. Check the conflict message, unchanged stock on rejection, corrected cart, successful new review, and immutable older orders.
  • Check keyboard navigation, visible focus, accessible button names, mobile layout, API errors, and recovery after a lost confirmation. Stable hooks include cart-item, cart-line-total, cart-total, place-order, order-confirmation, order-number, order-row, and order-item. Scope repeated hooks to their product or order.

Reproduce price and stock changes locally

In a second CMD terminal in the application folder, run the following deliberate demo change. It does not reset accounts or rewrite saved orders. It is a local command, not a web endpoint, and is disabled in production. No rebuild is needed. 

npm.cmd run demo:product -- --sku SR-101 --stock 1 --price-cents 13900

To restore that product's starting values for a new scenario, use the command below. Restoring these values is an intentional stock edit; it does not cancel orders. Use the full demo reset only when you intend to discard all carts, orders, and sessions and generate new passwords. 

npm.cmd run demo:product -- --sku SR-101 --stock 18 --price-cents 12900

RELEASE GUIDE · SECURITY

Security and delivery checks

The application checks permissions on the server, stores protected passwords and sessions, validates submitted values, limits login attempts, and rejects forged changes. Customer responses exclude staff-only information. Error messages avoid exposing passwords or internal failures. There are no deliberately introduced defects in this baseline.

The security baseline follows relevant OWASP ASVS guidance. This is a local demo with fictional data; it has not received an independent penetration test or certification. Local HTTP is restricted to this computer. Public hosting requires a separate HTTPS and deployment review.

Earlier increment 1 developer verification

  • TypeScript checks and an optimized production build passed.
  • Seventy temporary developer API checks passed against the requested local installation. They covered authentication, validation, filtering, sorting with equal values, pagination, staff permissions, session expiry, logout revocation, and login limits.
  • The dependency advisory check reported zero known advisories after updating the validation library. This is a point-in-time check.
  • Browser checks covered customer sign-in, the catalog layout, combined filters, product details, and the additional journeys recorded in the delivery verification note.

These earlier development checks do not replace the learner's independent Playwright suite. The learner reports 144 passing executions for increment 1. Current increment 2 developer verification is recorded in docs/VERIFICATION.md.

Practices to carry into your framework

Use independent sessions and data, verify important outcomes, and keep tests readable. The UI includes accessible roles and labels, selected test IDs, stable HTML IDs, and stable classes. Repeated product cards and inventory rows give you opportunities to filter and chain locators. A locator strategy should favour clarity and stability over unnecessary complexity.

Local demo tradeoffs

Prepared accounts keep this release focused; real products normally need a reviewed account lifecycle. The local database is suitable for this small training environment. Its built-in SQLite interface is experimental in the installed Node runtime, so runtime and database choices must be reviewed before production use. The local login limiter also needs a different design for multiple application servers.

Restore the starting data

Stop Stockroom and run npm.cmd run demo:reset from its application folder. This deletes all carts and orders, recreates the fictional data, invalidates sessions, clears login limits, and generates new passwords in the local account file. Restart the application afterwards. Use this only when you intend to discard the current demo state.
